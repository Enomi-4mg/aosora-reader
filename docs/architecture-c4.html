青空Reader アーキテクチャ — C4 モデル

青空文庫デスクトップリーダー（Electron + React + TypeScript / macOS）のリポジトリ構造

出典: src/ の実装（2026-10-23 時点 / main ブランチ c4875ad）。 読む順番とデータ構造の解説は docs/CODE_GUIDE.md、設計の不変条件は README.md にある。

Lv1 — システムコンテキスト

誰が使い、どの外部システムに依存するか。アプリ本体はオフラインで完結し、 通信するのは「作品を取り込むとき」と「辞書を引くとき」だけ。どちらが失敗しても本文閲覧・注釈・読み上げは止まらない。

外部依存と失敗時の振る舞い

相手やりとり実装失敗したとき
青空文庫作品カタログ ZIP の取得、本文 TXT のダウンロード AozoraCatalogService（接続先は aozora.gr.jp に限定） 取り込みだけが失敗。既存の本棚と読書は無関係に動く
日本語版 Wiktionary選択語の意味を検索 WiktionaryProvider（DictionaryProvider 境界の実装） 空の結果を返すだけ。例外は Reader に伝播しない
macOS読み上げ音声、クリップボード、ファイル選択ダイアログ、Finder、既定ブラウザ renderer の Web Speech API / main の clipboard・dialog・shell 読み上げ非対応なら TTS UI を出さない
X / LINE作品カードの共有 URL を既定ブラウザで開く ShareMenu.shareUrls() → shell.openExternal 共有だけが行われない
アプリ内で任意のページを開かせない。 setWindowOpenHandler と will-navigate の両方を塞ぎ、http(s) は既定ブラウザへ逃がす。 ドロップされたファイルやリンクによるトップレベル遷移も同じ経路で止める。

Lv2 — コンテナ

プロセスと永続化の境界。renderer は fs にも SQLite にも触らず、 window.aozora の 38 本の型付き関数だけを通る。青空文庫記法の知識は shared/parser に閉じ、 renderer は Document Model しか見ない。

コンテナ一覧

コンテナ技術責務越えてはいけない境界
RendererChromium / React 19 / Zustand Document Model の描画、ページ幾何、注釈 UI、読み上げ Node API を使わない。青空文庫記法を解釈しない
preloadElectron preload / contextBridge IPC_CHANNELS から API を機械的に生成し window.aozora に公開 ロジックを持たない。ipcRenderer を renderer に渡さない
Main プロセスNode 22 / Electron main IPC ハンドラ、Service、Repository、取り込み、通信、OS 連携 SQL を Repository の外に出さない。ParseIssue を renderer に出さない
shared/TypeScript（純粋関数のみ） Document Model、TextPosition、青空文庫パーサー、外字表、IPC 型 DOM・React・DB・Electron に依存しない
library.dbSQLite（node:sqlite）/ WAL books・chapters・blocks・注釈・進捗・セッション・設定 ページ番号を保存しない。保存するのは TextPosition だけ
userData/fonts/ファイル + fonts.json ユーザーが追加したフォント本体と表示名 renderer へはバイト列（getFontData）としてのみ渡す

IPC の形

  • shared/ipc.ts の AozoraIpcApi が唯一の契約。チャネル名は IPC_CHANNELS と型で一対一に縛られ、 書き忘れると _AllChannelsListed でコンパイルが落ちる。
  • main 側は handlers オブジェクトを ipcMain.handle に一括登録し、 例外はログに出して短いメッセージだけ renderer に返す（DB 書き込み失敗でアプリを落とさない）。
  • パースは取り込み時に一度だけ。Document Model を DB に保存するのは速度ではなく、 blockId を固定してハイライトを orphan にしないため。

Lv3 — コンポーネント

コンテナの内側。main は「IPC ハンドラ → Service / Repository → 1 本の DB 接続」、 renderer は「View → store → IPC」と「Document Model → DOM → TextPosition」の 2 系統でできている。

Lv4 — コード（位置情報のデータフロー）

このアプリで唯一壊れやすいのは機能ではなく位置情報なので、Lv4 ではクラス図ではなく 「選択 → 保存 → 再表示」の経路を示す。ハイライト・検索一致・読み上げ位置は、すべてこの同じ経路を通る。

不変条件がどこで守られているか

不変条件内容守っている場所
A — plainText が唯一の座標空間 オフセットは UTF-16 コードユニット。ルビの読みは含めず、未対応注記はゼロ幅（start === end） shared/parser/inline.ts、shared/model/document.ts、reader/dom/contract.ts
B — ページ送りは画面上の左右移動に統一 横書きは translateX(-pageWidth)、縦書きは translateX(+pageWidth)。ページ番号は保存せず毎回幾何から導出 reader/layout/LayoutController.ts
系 — 塗りは CSS Custom Highlight API に集約 ハイライト・検索一致・読み上げ中の文を自前オーバーレイで描かない。実表示色は ::highlight() reader/dom/highlightPainter.ts、styles/theme.css
再パースしない 取り込み時に一度だけパースして Document Model を保存。blockId が変わらないので既存の注釈が orphan にならない main/services/ImportService.ts、BookRepository

検証の構造

  • npm test — ユニットテスト（test/）。パーサー・位置計算・ストア・DB ラウンドトリップ。
  • scripts/probe-samples.mjs — 手元の実ファイルに対するパース検査（実データはリポジトリに含めない）。
  • scripts/e2e-reader.mjs — レイアウトが絡む項目は jsdom では検証できないため、実 Electron 上で確認する。
  • scripts/check-legibility.mjs — ルビの実効サイズ、行の接触、コントラスト比を数値で判定する。目視の印象は使わない。
  • scripts/spike-layout.mjs — 不変条件 B を実測したスパイク。Electron を上げ直したときの回帰確認用。

線の意味

  • 実線の矢印 — 実行時の呼び出しやデータの流れ。矢印の向きが呼び出す側 → 呼ばれる側。
  • 破線の矢印 — 型と純粋関数の利用（import）。実行時の依存ではない。
  • 破線の枠 — プロセスやアプリの境界（システムバウンダリ）。
  • 折れ線 — 図の見やすさのために経路を曲げただけで、意味の違いはない。
